## gallery 房间：点照片 → 直接看大图（去掉 Project Detail 翻面）+ 收尾贴图

### 弹窗背景的答案（要记住，以后还会被问）

Project Detail 那个弹窗**不是弹窗，是 DOM 浮层** `src/components/ui/GlobalOverlay.jsx`，
由 `SceneContext` 的 `overlayContent` 驱动，全站共用（About 奖状 / Studio 屏幕也用它）。
它的纸张底纹**引用了图片**：
`src/styles/GlobalOverlay.scss` → `.studio-paper-card::before { background: url('/textures/paper-texture.webp') }`。
撕纸边（`clip-path`）、聚光遮罩（`radial-gradient` + `mask-image`）、回弹入场都是 CSS，
**只有那层底纹是位图**。

`paper-texture.webp`（22 KB）目前**仍在用**，一共 11 处：
3D 侧 `App.jsx` / `Corridor.jsx` / `Tunnel.jsx` / `PaperBackground.jsx`（`useTexture`），
样式侧 `Preloader.scss` / `NavigationUI.scss`（3 处）/ `GlobalOverlay.scss` / `AchievementsPanel.scss`。
→ **没有动它**。它撑起的是全站纸感，要转程序化应该单独开一轮，不该顺手改。

### 交互改造（本次实际做的）

根因很省事：**卡片的正面本身就是照片**。`photoPlaceholderTexture()`（`src/utils/photoPlaceholder.js`）
画的是 768×1024，和卡片平面 1.5×2 **同为 0.75 比例**，铺满整张卡不留边。
所以「翻到背面看 PROJECT DETAILS」这件事本身就是多余的 —— 打开 = 不翻面 + 放大。

`ProjectCard.openCard()` 里：
- 落位旋转 `rotation.x: Math.PI * 0.8 → −0.06 → Math.PI` 改为 `−0.06 → 0`（**停在正面**）
- 中途「反向摆一下」让拾起感成立，但终点不再翻面
- `bend: −0.3` → `0.25 → 0`，**把纸浪压平**（照片不该被皱）
- 终点加 `z: 0.012` 微倾，免得像一块硬纸板
- 放大 1.1 → **`CARD_OPEN_SCALE = 1.32`**（新增常量，在文件顶部的 tunables 区）

`closeCard()` 本来就把 `rotation.x` 归零，一行都不用改。

### 踩坑（探针相关，都是这次新踩的）

1. **`__aispin.snap(id)` 不会把相机送进房间**。它只设 `__forceRoom` + `enterRoom` + 把相机放到
   「门上 8 单位」（而房间内部还挂在 DoorSection 那个带旋转的组里），所以拿它做布局探针
   会一直拍在门板上。**要真实相机位就老老实实 `enter()` + `teleport(id)` + 等 15 s**。
2. **别用「卡片离『卡片质心』最近」来选目标卡** —— 质心不在相机视野中央，选出来的经常
   直接投影到屏幕外（实测 sx = 2152）。**按屏幕投影到画面中心的距离选**才对。
3. **点击没反应时先分清「事件没到」还是「射线没中」**：在 `window` 上捕获
   `pointerdown/up/click` 就能证明事件到了 canvas；再用「射线 × 平面」自己求交，
   打印 `dx/dy` 看是否落在 `|dx| <= w/2 && |dy| <= h/2` 内。两者都通过却仍无效，
   就是应用层（如 `isAnimating` 守卫）的问题。
4. **不用 three 的 Raycaster 也能做求交**：`__THREE__` 只挂了版本号，`window.Raycaster` 是
   `undefined`。用 `camera.position.constructor` 当 Vector3 足够，手写
   `t = (p − o)·n / (n·d)` 即可，`n` 用 `new K(0,0,1).transformDirection(mesh.matrixWorld)`。
5. **`Object3D.matrixWorld.decompose()` 拿到的四元数不是 Euler**，`setFromQuaternion` 那套
   在探针里容易写错（`quaternion.setFromRotationMatrix is not a function`）。
   要旋转角度就直接读 `obj.rotation.x` / `obj.parent.scale.x`，简单可靠。

## 两个严重 bug 修复（同日下午）

用户报：「1、进门后地板闪现绿色的草地，闪了几次才恢复。2、偶发房间不出现的情况（所有的房间都不出现）」

### BUG 1 · 进门时地板闪绿 —— 入口草皮与走廊地板**完全共面**

不是「闪一下」，是**两个共面平面在深度测试里互相抢**。

- 入口草皮 `EmptyCorridor.jsx`：`position={[0, -corridorHeight/2, ...]}` → `corridorHeight 3.5` → **y = −1.75**
- 走廊地板 `CorridorWalls.jsx`：`corridorHeight 3.5` → **y = −1.75**
- 入口地面 `EntranceDoors.jsx` 的 `floorY`：**−1.75**

三者一模一样。而草皮是 **25×40** 的，走廊只有 **7 宽** —— 草皮把整个街区都铺了，
所以在门洞那一带（z ≈ 10…22）它和走廊地板大面积重叠。
入场相机从 z28 飞到 z11，**正好横穿这段重叠区**；两个共面面片在移动的相机下不只是
z-fighting —— 视距连续变化会让深度测试**整体翻转**，于是走廊地板看起来「变绿」，
`hasEntered` 把草皮卸掉之前会翻好几次。这完全对得上「闪了几次才恢复」。

**修法**：给草皮一个 `GROUND_DROP = 0.02`，落到 `-1.75 - 0.02 = -1.77`。
走廊地板就永远稳赢深度测试，而草皮在所有走廊没盖到的地方（大门前、墙外）依然可见。
0.02 在 11 单位视距下约是深度缓冲精度的 3000 倍，所以这不是个「调出来的数字」。

实测：`entranceGrassY: [-1.77]`、`corridorFloorY: [-1.75]`、`coplanar: false`、`minGap: 0.02`。

⚠️ **教训**：这个项目里「共面」是个系统性问题 —— 入口 / 走廊 / 房间三个模块各自
独立定义了 `floorY = -1.75`（连 `-corridorHeight/2` 都算了两遍）。以后新增任何地面
装饰，**先确认它和地板的确切 y 差**，别再往 −1.75 上叠。

### BUG 2 · 偶发所有房间都不出现 —— 传送状态机被无关重渲染杀掉

**根因（决定性）**：`PaperTransition.jsx` 的传送时间轴，dependency array 里有 `play`：

```js
}, [teleportPhase, startTeleportTransition, finishPaperOpen, play]);  // ← play 是关键
```

而 `play` 来自 `useAudio()`，**每次 `isMuted` / `globalVolume` 变化都会重建**
（`AudioManager.jsx` 的 `play = useCallback(..., [isMuted, globalVolume])`）。
所以**任何音量变动** —— 用户拖 SFX 滑块，或者**成就弹窗自己调的 `setGlobalVolume(0/1)`**
（进大门时就触发 `corridor_enter` 成就）—— 都会重跑这个 effect，而它的 cleanup 是：

```js
if (timelineRef.current) timelineRef.current.kill();
```

→ **把还在跑的时间轴杀掉**。时间轴一死，`onComplete` 永不触发，相位机卡住：

- 卡在 `'closing'`：相机不动、纸幕扣死、**并且 `isTeleporting` 永不清除** →
  `teleportTo()` 里 `if (isTeleporting) return` 会**拒绝之后每一次传送** →
  「所有房间都不出现」，还会永久持续。
- 卡在 `'opening'`：把纸幕归位到 `display:none` 的那段淡出在同一个被杀的时间轴里 →
  纸幕一直不透明地盖在房间上。

**A/B 反证（拿到了实锤）**：把旧写法放回去（不稳定的 deps + 关掉安全网），
在传送开始后 250ms 触发滑块 `input`，17 秒后：

```
{"room":null,"tp":true,"phase":"teleporting","paper":"display: block, opacity: 1"}
```

**纸幕整屏盖住、房间从未出现、`isTeleporting` 卡死** —— 症状与用户描述完全一致。

修好后同一场景（而且连打 3 次滑块）：
```
{"room":"gallery","tp":false,"phase":null,"paper":"none"}
```

**修法（三层）**：

1. **`PaperTransition` 的回调改走 ref**（`startTransitionRef` / `finishOpenRef` / `playRef`），
   dependency array 只留 `[teleportPhase]`。这样无关重渲染再也无法取消正在进行的传送。
2. **相位推进加「一次且仅一次」护栏 + 看门狗定时器**：`advanceOnce` 保证
   `startTeleportTransition` / `finishPaperOpen` 每个相位只调一次（gsap 的 onComplete
   与超时谁先到谁生效）；`closing` 0.8s 的 tween 配 1200ms 兜底、
   `opening` 1.2s 配 1600ms 兜底。**即使时间轴仍被意外杀掉，相位机也会继续走。**
3. **`phase` 为空时强制把纸幕归位**（`gsap.set(container, { opacity: 0, display: 'none' })`）。
   以前只有 `'opening'` 的淡出才会 `display:none`，所以任何跳过 `opening` 的路径
   （传送中途被取消、状态被下面的看门狗重置）都会把纸幕永久留在屏幕上。
   加上这一条，「什么都没发生」这个状态是自愈的。

**外加 `SceneContext` 的传送看门狗**（`TELEPORT_WATCHDOG_MS = 25000`）：
`teleportTo` 时起 25 秒定时器，`enterRoom` / `finishPaperOpen` / `cancelTeleport` 时清掉；
超时就强制释放 `isTeleporting` 等标志并 `console.warn`。
健康的一次进入约 1–2 秒（DoorSection 自己的房间加载兜底是 8 秒），
所以这只是最后一道逃生口 —— 但有了它，**任何未来的卡死都只能造成一次失败，
而不会永久废掉整个地图**。

### 顺带加固：`DoorSection` 两处「设置了 isAnimating 却提前 return」

- `handleClick` 中途 `if (!groupRef.current) return;` —— 此时 `setIsAnimating(true)` 已经执行过，
  而 `enterRoom()` 的 250ms 延时回调是**唯一**会把它清掉的地方 → 永远 true →
  `handleClick` 里的 `if (isAnimating) return` 会**永久忽略这扇门的所有点击**。
- `openDoor` 开头 `if (!doorRef.current) return;` —— 同样是「房间加载完要调用它」的唯一出口，
  直接 return 就没人解锁了。

两处都补上了 `setIsAnimating(false)` + `setIsTiltLocked(false)` 再返回。
这类「先设状态、后提前返回」的写法是这个文件里反复出现的隐患，值得全文再审一遍。

## 把「点了没反应」变成可见的 toast 提示

接上一条：我提出「`teleportTo` 的守卫静默 return，用户会觉得地图坏了」，
用户回「看起来像『点了没反应』，可以弹 toast 提示吗？」→ 做了。

### 现状盘点

项目里**原本没有任何 toast / 通知机制**（grep `toast|snackbar|notification` 全空）。
但它已经有一套很干净的「跨层通信」惯例：`window.dispatchEvent(new CustomEvent(...))`，
用在 `aispin-language-change` 和 `sw-update-ready` 上。所以 toast 也照这个套路做，
**不引入 context** —— 因为需要报警的调用方有一部分**不在 React 渲染树里**
（`SceneContext` 的守卫、R3F 的指针处理器），走 context 会让每个消费者都跟着重渲染。

### 新增三个文件

- **`src/utils/toast.js`** —— `showToast(message, { duration })`。
  fire-and-forget，派发 `aispin-toast` 事件；空字符串直接忽略。这层不碰 React。
- **`src/components/ui/Toast.jsx`** —— 唯一监听者，渲染队列。两个特意做的行为：
  1. **相同文案折叠**：如果新来的消息和**最新可见的那条**一样，只**刷新它的计时器**，
     不再压一条。这样用户反复点同一个东西只会看到一条稳定的提示，而不是堆成一摞。
  2. **最多同时 3 条**（`MAX_VISIBLE`），超出丢最旧的，一批爆发也盖不住场景。
- **`src/styles/Toast.scss`** —— 磨砂纸风格，和 `AchievementPopup` 同一套材质
  （`rgba(255,246,233,.72)` + `backdrop-filter: blur(14px)`），
  这样两者看起来是**同一族反馈**而不是两套系统；带深色主题与
  `prefers-reduced-motion` 分支。

### 位置与层级（这里有个坑）

- 成就弹窗也在底部居中：`bottom: 32px`、高约 50px、`z-index: 110`。
  **两者可能同时出现**（进房间正好会触发成就，而进房间正是传送守卫最可能说话的时机），
  所以 toast 锚在 `bottom: 100px` 而不是抢占同一位置。
- 层级取 **300**：高于 nav(100) 与成就弹窗(110)，低于 `GlobalOverlay`(2000)，
  这样全屏弹窗仍能盖住 toast。
- **`pointer-events: none`** 是必须的 —— toast 是纯反馈，绝不能吞掉点击。
  实测：`elementFromPoint(toast 中心).className === 'CANVAS'`，即点到的是画布。

### 无障碍：live region 必须常驻

一开始写成 `if (!toasts.length) return null`，这是**错的**：
`aria-live` 区域只有在**添加内容之前就已存在于 DOM** 时才会被读屏软件播报，
空闲时返回 null 会让第一条 toast 连同容器一起挂载，于是**永远读不出来**。
改成始终渲染容器（空容器不可见），实测 `role="status"` / `aria-live="polite"` 常驻。

### 接在哪些守卫上

| 位置 | 触发条件 | 文案 |
|---|---|---|
| `SceneContext.teleportTo` | 目标房间 === 当前房间 | 已经在「{房间}」里了 / Already in {ROOM} |
| `SceneContext.teleportTo` | 传送进行中 | 正在传送中，请稍候… / Teleport in progress… |
| `DoorSection.handleClick` | 门动画中又被点（`isAnimating`） | 门还在动，稍等一下 / Still opening — one moment |

- 房间名走 `ROOMS[].zh/en`，所以是「摄影 / GALLERY」而不是内部 id。
- `SceneProvider` 现在读 `useSitePreferences()` 拿 `language`
  —— 安全，因为 App.jsx 里 `SitePreferencesProvider` 一直包着 `SceneProvider`。
- **门的 busy 提示只在真实点击时弹**：传送流程会用 `e.isTeleport` 程序化调用
  `handleClick`，那条路径必须保持安静（`if (!isTeleport) showToast(...)`）。

### 验证（真实交互距离，不是硬编码坐标）

⚠️ 这次踩了一个探针的坑，值得记：**`Vector3.project()` 对相机背后的点会给「镜像」结果**，
看起来像在屏幕中央，其实在背后 —— 不加 `if (v.z >= cam.z - k) return` 的过滤会捞出一堆假目标。
而且**走廊里的门在默认机位下距离 28 单位、`normal·toCam` 只有 0.05–0.12（几乎与视线平行）**，
在那个距离/角度点门本来就不合理，点不中不代表代码有问题。

正确路径：先 `teleport` 进房间，再点 `button[aria-label="Back to corridor"]` 出来
→ 相机落在 `(0, 0.2, −16)`，门在 6.5 单位外、`normal·toCam = 0.77`，**这才是真实交互距离**。

结果：
- 同房间请求 → `["已经在「摄影」里了"]`
- 传送中再请求 → `["已经在「摄影」里了", "正在传送中，请稍候…"]`
- 切到英文后 → `["Already in GALLERY"]` / `["Teleport in progress…"]`

## 「房间不见」的真正根因（第三个 bug，与传送无关）—— 分段可见性判据用错了参照系

用户给了精确复现：「1、进入楼廊 2、然后往后退，此时走廊的房间消失了。再往前进也看不到了。」

### 根因：`isFarAhead` 以分段自身的 `startZ` 为基准

`InfiniteCorridorManager.jsx` 的 `SegmentVisibilityWrapper`：

```js
const startZ = 10 - (segmentIndex * SEGMENT_LENGTH);
const endZ   = startZ - SEGMENT_LENGTH;
const isFarAhead = camera.position.z > startZ + 30;   // ← 错在这里
```

这行想表达「相机还没走到这一段」，但它把 `startZ` 当成了参照系。
**相机可以从这一段的 `startZ` 之外看向它** —— 而且一开始就是这样：
相机出生在 `z = 28`，而 segment 0 的 `startZ = 10`。

再看 `useInfiniteCamera` 的滚动：
```js
const delta = e.deltaY * scrollSpeed;   // scrollSpeed 0.025
targetZ.current -= delta;               // 向下滚 = 前进；向上滚 = 后退
```
**`targetZ` 完全没有上下界钳制** —— 用户可以无限后退。

于是只需后退到 `z > 40`，segment 0 就自杀式隐藏。**而 segment 0 独占四个房间门**
（档案/摄影/工作室/文稿），所以用户看到的就是「房间全没了」，并且在走回 `z < 40` 之前
一直不恢复。完全吻合「再往前进也看不到了」（他还没走回那个阈值）。

### 实测数据（修复前）

| 相机 z | segment 0 可见 |
|---|---|
| 10.3 | ✅ 可见（正常） |
| 24.8 | ✅ |
| **40.4** | ❌ **隐藏** ← 正是阈值处 |

一过 `z = 40` 立刻翻脸，且是**硬切**（`isFarAhead` 没有任何余量）。

### 修法（两层）

1. **改用「分段索引」比较，不再用世界 Z**：
   ```js
   const cameraSegment = Math.floor((10 - z) / SEGMENT_LENGTH);
   const isAhead = segmentIndex > cameraSegment + 1;   // 只藏「我在的这一段之后的下一段」
   ```
   这与该文件本来的设计意图一致（`shouldBeActive = [current-1, current, current+1]`
   —— 挂载上一段/当前段/下一段），但**藏的是相对的「再往前那一段」**，
   所以相机站在哪里都对。`fogFar = 60`，一整个分段 80 单位早就在雾外，看不到忽然冒出来。

2. **硬保证**：`if (segmentIndex === cameraSegment) isVisible = true`。
   两个启发式判据万一不一致，也**永远不允许把相机所站的那一段藏掉** ——
   从「偶发整条走廊全黑」变成不可能。

### 验证

- **失效区间实测**：`z = 66.1` / `z = 67.9` 时 `seg0: true`，截图里右侧「摄影」门清晰可见
  （`dead-C-back2.png` / `final-1-dead-zone.png`）
- **完整来回扫描**（z 从 −1 退到 +201 再回到 −8，每步都探）：
  `seg0_visible` 在 z ≤ 81 恒为 true，永不与 `cameraSegment` 冲突
- **端到端复刻用户路径**：进入 → 后退 → 前进 → **点击「摄影」门 → `room: "gallery"`，
  房间正常打开**（`accept-room-open.png`），且无 toast 残留
- `vite build` 730 modules；`=== ERRORS (0) ===`
- 截图归档 `.workbuddy-ai/shots/segment-visible-fix/`

### 教训（这条比修 bug 本身重要）

**三个 bug 里有两个的根因是同一个模式：把「某个阈值」挂在了错误的参照系上。**
- 传送状态机：参照系是**不稳定的回调身份**（`play`）而不是事件
- 分段可见性：参照系是**分段自己的 startZ** 而不是相机所处的分段

共同症状都是「偶发、刷新就好、一旦触发就持续」。**排查这类问题要先问：
这个判据的参照系在什么情况下会失效？** 而不是先去调阈值大小。

另外：**用户能给出精确复现步骤时，优先照着复刻，不要去猜。**
我前两轮一直在传送/弹窗那条线上找，方向错了；用户一句「往后退」直接指向了
一个我从未检查过的模块。

## HUD 统一（右上 5 图标 + 左上返回）+ 修「进了房子出不来」

用户两条：
1. 右上、左上的操作按钮还是旧样式，要改成和「语言切换」图标一样的颜色；
   音乐/成就也要一直固定在右上角。即页面加载完后右上角自上而下拉出 5 个 ICON：
   地图、语言、暗黑模式、音乐设置、成就；左边是后退 ICON，进房间后自上而下滑出。
2. BUG：进入房子后没办法退出到房子最外面（在走廊时后退按钮没出现）。

### 背景：为什么会有「两种按钮样式」

其实有**两处**都在管右上角，这是历史遗留：

| 组件 | 位置 | 按钮 | 样式 | 出现时机 |
|---|---|---|---|---|
| `SiteControls` | 右上 | 地图 / 语言 / 暗黑 | 扁平奶油药丸 `.hud-btn`（就是语言按钮的样式） | 一直可见 |
| `NavigationUI` | 右上 | 音乐 / 成就 | `.nav-btn`：50×55 撕纸卡片 + 手绘 SVG 边框 + 写死 `#1a1a1a` | 只在 `hasEntered` 之后 |

两边很少同屏对比，但合在一起就是「两个不同的产品」。用户看到的就是后者。

### 做法：抽出共享样式 + 把 5 个按钮收进一个组件

- 新增 **`src/styles/HudControls.scss`**：`.hud-cluster`（fixed，纵向 flex，带
  `--left` / `--right` 修饰符）+ `.hud-btn`（就是语言按钮那一套：
  `rgba(255,246,233,.94)` / `#5A4636` / `border-radius:999px` / 42×42）。
  **在 `main.scss` 里全局 `@use`**，这样规则先于各组件样式表落地，
  两个组件都不必依赖对方的导入顺序。
- **逐个下拉**：`.hud-btn` 统一挂 `hudDropIn` 动画，靠 inline `animationDelay`
  （`index * 70ms`）错开 —— 于是右上角看起来是「一列图标被从顶边拉出来」。
  左上返回按钮复用同一个动画。
- **`SiteControls` 现在渲染全部 5 个**按钮：地图、语言、暗黑、音频、成就。
  后两个原本在 `NavigationUI` 里，现在只把**面板**留在那儿（音频卡片是它的布局一部分，
  `<AchievementsPanel />` 是它的子组件），按钮和面板用 window 事件对话 ——
  和原来地图的做法一致：`hudToggle`（按钮→面板）+ `hudState`（面板→按钮，
  用于 `is-open` 高亮）。旧的 `toggleMap` / `mapStateChange` 一并换掉。
- 音频面板**去掉 `hasEntered` 门禁**（按钮现在一直可见，面板必须也能从入口打开）。
- 删除旧样式：`.nav-btn` / `.nav-controls` / `.hamburger-btn`（后者已无任何消费者），
  以及随之失效的 `isUIHidden` 状态和 `isMuted` 解构。
  连注释里引用的「旧样式」也一并清掉，NavigationUI.scss 从 700+ 行降到 638 行。

### BUG：`hasEntered` 是个单向闩锁

`setHasEntered(true)` 之后**全代码库没有任何地方把它设回 false**
（grep 确认：只有 `markEntered` 一处写入）。而入口大门场景是
`{!hasEntered && <EntranceDoors/>}`、`{!hasEntered && <EmptyCorridor/>}`
—— 一进门就**永久卸载**。所以「走出房子」这条路在物理上根本不存在，
而后退按钮又只在 `isInRoom` 时渲染 → 走廊里按钮消失、也走不出去。

按用户选择做成**两级返回**：
- 在房间里 → 回走廊（走 `requestExit()`，DoorSection 原来的反向飞出动效）
- 在走廊里 → 走出房子（新逻辑）

**新增 `src/components/canvas/corridor/HouseExit.jsx`**：把相机从当前位置平滑移回门外
`(0, 0.2, 28)` 并归零旋转（1.3s，和入口飞入同节奏），到达后调 `markExited()`。
为什么必须是 3D 组件：返回按钮在 DOM 里，但**只有 canvas 内部能操作相机** ——
这正是 `TeleportRoom` 处理传送相机的方式，照抄它。

**关键坑：滚动 hook 必须让位。** `useInfiniteCamera` 在 `scrollEnabled` 时**每帧**
写 `camera.position.z`，而退出恰恰发生在滚动启用状态（人站在走廊里）。
两者会抢同一个轴 → 相机卡在半路/橡皮筋。所以 `Experience.jsx` 里
`scrollEnabled` / `parallaxEnabled` 都加上 `&& !houseExitRequested`。

**另一个刻意的顺序**：入口场景是在**滑行结束后**才重新挂载（`markExited()` 里清
`hasEntered`），不是一按按钮就挂。否则关着的两扇大门会正好落在相机的飞行路径上，
相机出屋时会直接从门里穿过去。

`SceneContext` 新增：`houseExitRequested` / `requestHouseExit()` / `markExited()`。
`markExited` 一次把 `hasEntered`、`currentRoom`、`exitRequested`、`overlayContent` 全清回初始态。

## 地板接缝：改细、改灰白

用户：「地板的灰黑色接缝太大了，改小，颜色改为灰白」

接缝在 `src/shaders/roomSurfaces.js` 的 `WOOD_FLOOR_FRAG`（`makeFloorMaterial()`，
用在**走廊地板**和**房间前厅地板**）。原实现：

```glsl
float seamV = smoothstep(0.012, 0.070, edgeV);
float seamU = smoothstep(0.010, 0.055, edgeU);
col = mix(col * 0.68, col, min(seamV, seamU));      // ← 暗到 68%
float bev = ...; col += vec3(0.022, 0.019, 0.014) * bev;   // 内侧提亮
```

问题有两层：**宽度**（到 7% 板宽，即每侧 ~4.3 cm，整个接缝带 ~10 cm）和
**颜色**（压到 68% 亮度并带棕调 → 在浅橡木地板上就是一道近黑的线）。

### 改法

```glsl
float seamV = smoothstep(0.004, 0.018, edgeV);
float seamU = smoothstep(0.002, 0.010, edgeU);
float seamMask = 1.0 - min(seamV, seamU);
float seamFade = 1.0 - smoothstep(5.0, 24.0, vViewZ);   // 远处淡出
vec3 seamCol = vec3(0.930, 0.918, 0.896);               // 暖调灰白
col = mix(col, seamCol, seamMask * seamFade);
```

- **变细约 3.8 倍**：可见带从 ~7.3 cm 降到 **~1.9 cm**
- **由「压暗」改成「提亮」**：新接缝比板面**亮** 21/255，而非暗 68/255 ——
  这就是石灰洗白 / 白油橡木拼缝的观感。木板之间的区分交给上面的 per-board tone，
  接缝只负责暗示边缘。
- **删掉内侧的 `bev` 提亮**：它原本是给「暗接缝」做湿边反光的；配浅接缝会变成
  第二道更宽的亮带，反而更脏。
- **加视深淡出**（`seamFade`，5→24 m）。这条是必须的：地板是**一个只有 4 个顶点的
  quad**（见 `CorridorWalls` 的 `floorGeometry`），用世界米采样、**没有 mip 链**，
  亚厘米级的细线在走廊那种掠射角下没有任何东西能过滤它，远处会爬满闪烁的噪点。
  淡出后既干净，又像景深。

### 新增 `FLOOR_VERT`（没动 `ROOM_VERT`）

要实现视深淡出就得把视深传进片元着色器。**特意新写了一个顶点着色器**而不是给
`ROOM_VERT` 加 varying：墙面/天花板/踢脚线**共用** `ROOM_VERT`，而它们的片元着色器
并不声明 `vViewZ`。写一个片元端不读的 varying 在 GLSL 里合法，但正是那种
「一个驱动能过、另一个驱动给警告」的写法，而且这些表面本来也没必要背它。

### 效果对比（按 shader 公式精确重算）

| | 板面 | 接缝最深色 | 与板面对比 | 可见带宽 |
|---|---|---|---|---|
| 旧 | `229,213,186` | `156,145,126` | **暗 68/255** | **7.29 cm** |
| 新 | `229,213,186` | `237,234,228` | **亮 21/255** | **1.92 cm** |

⚠️ 量宽度时的坑：我第一版判据写成「偏离板面 < 2%」，
而 `smoothstep` 在边缘处导数很小，导致两个版本的量出来都是 `0.03 cm` —— 假结果。
正确做法是**每侧各自归一化**（判据 = 自己峰值的 10%），才能公平比较两者宽度。

### 验证

- 走廊与前厅实拍：接缝是细的浅灰白线，板面仍是原来的浅橡木
- `vite build` 731 modules；`=== ERRORS (0) ===`
- 截图 + 剖面图归档 `.workbuddy-ai/shots/floor-seams/`
  （`seam-profile-comparison.png` 是旧/新各铺三条板宽的横截面对比）

同名的还有 `proceduralTextures.js` 的 `woodFloorTexture()`（gallery 房间地板），
它走 canvas + mipmap 贴图路线、接缝是棕色调 `rgba(146,124,96,.55)`，

## 两个 bug：门动画中按返回导致永久卡死 + 下拉浮层压住图标

用户：
1. 进房子后穿过一扇门、倒退出来，触发「所有房间不再出现」，且左上返回按钮点了没反应
2. 菜单/探索下拉浮层出现时和左侧 icon 按钮重叠

### BUG 1 · 门动画进行中被返回键打断 → 状态永久卡死

用户描述的「倒退出来」我一开始理解错了方向。真实机制是一串连锁反应，
而且**是我上一轮加的 `HouseExit` 引入的**：

1. 点门进房，`DoorSection` 开始 1.5s 相机飞入，期间 `isAnimating = true`
2. 用户此时点左上返回 → `requestHouseExit()` → `HouseExit` 开始滑行
3. 旧的 `HouseExit` 第一件事就是 **`gsap.killTweensOf(camera.position)`**
   —— 它把门飞入的补间**连同 `onComplete` 一起杀掉**
4. 那个 `onComplete` 是 `DoorSection` 里**唯一**负责「进房完成」的地方：
   `setIsInsideRoom(true)` → `enterRoom()` → 解锁 `isAnimating` → 交还相机
   → 全部丢失。门永久停在半开、`isAnimating` 永远为 true
5. `isAnimating` 是**入场锁**：`handleClick` 和 `exitRoom` 都以它做守卫
   → **这扇门之后再也点不动**，看起来就是「返回按钮也没反应」
6. 相机覆盖（`setCameraOverride(true)`）也永不释放 → 走廊滚动被挂起

**四处修法：**

1. **`HouseExit` 不再抢占相机，改为等待**
   `gsap.getTweensOf(camera.position).length > 0` 时每 250ms 重试，最多等 6s。
   （重试用的 tick 必须进 `effect` 的依赖数组，否则定时器空转、effect 不重跑 ——
   我第一版就漏了，效果是「返回键静默失效」。）
2. **`SceneContext` 直接拒绝**，而不是排队。
   新增 `doorBusy` 状态，`requestHouseExit()` 在 `doorBusy` 为真时直接 return。
   排队是错的：请求会一直挂着，等用户之后退出房间时突然发动，把人自动滑出大门。
3. **返回按钮在 `doorBusy` 时 `disabled`**（`HUD` 加了 `:disabled` 的暗化样式）。
   点了没用至少要让用户看出来 —— 这也是上一轮 toast 同一条原则。
   实测：飞行中 `disabled: true`，点击无效（`ok: false`），落位后自动恢复可用。
4. **`closeDoor` 的完成回调改为必然执行**。
   `closeDoor(onDoorClosed)` 原来在 `!doorRef.current || !isOpen` 时**静默 return**，
   而 `exitRoom` 把**整套收尾**（`isAnimating` / `isInsideRoom` / `shouldRenderRoom` /
   `contextExitRoom` / 交还相机）都放在这个回调里 —— 一旦走了这条分支，五样全丢。
   现在把 `settle()` 提到最前面，任何提前返回都先调它。
5. **`DoorSection` 加 9 秒看门狗**：`isAnimating` 超过 9 秒仍为真就强制解锁
   （正常进出 1.5–3.5s）。效果是把「永久废掉这扇门」降级为「一次不流畅」。

### BUG 2 · 三个右上浮层全部压在图标列上

`.audio-panel`（220px）、`.achievements-panel`（280px）、`.map-panel` 清一色
`position:fixed; top:0; right:24px` —— 而这正是图标列所在的位置。

实测证据（1280×800）：音频面板矩形 `[1036, 0, 220, 152]`、
图标列 `[1216, 18, 46, 242]` → **相交，压住上面 3 个图标**。
地图面板窄屏下 `width: 95%/100%` 居中，会**同时压住左右两列**。

## 「往后退房间不见了」根因确认（未改代码）+ 与用户对齐空间模型

用户复现路径：「走过廊道里的门，看到主角，首次能看到主角后方墙壁上的门，
此时马上后退退出那个门，相当于退回到离主角最远的地方，这时候廊道所有的门就没有渲染了。」

### 根因：**走廊的雾**吃掉了房间门，不是隐藏、不是剔除、不是状态卡死

量化证据（`SCENE = { fogNear: 18, fogFar: 60 }`，门在 z = −8 / −22 / −38 / −52）：

| 相机 z | 最近门距离 | 雾权重 | 实际画面 |
|---|---|---|---|
| −1.5 | 7 | 1.00 | 门清晰、带「档案」标牌 |
| 28（刚进屋） | 36 | 0.57 | 门半透 |
| 42 | 50 | 0.24 | 很淡 |
| **57.6** | **66** | **0** | **一扇门都看不见** |

探针同一帧里的三个数字最能说明问题：
`doorsInScene: 4`、`vis: true`、`onScreen: true`，但 `doorsActuallyDrawn: 0`。
**门存在、没被隐藏、在视野内 —— 只是被雾完全吃掉。**

为什么「装饰都在、门没了」：走廊**装饰**（画框 / 通风口 / 边几 / 盆栽树）是
`meshBasicMaterial` 且**没开 fog**，多远都渲染；**门**是普通雾效材质。

为什么能退那么远：`useInfiniteCamera` 的 `targetZ` **完全没有边界**，
而 **segment −1 本身一扇房间门都没有**（见下）。所以「往后退」= 退进一段空廊道，
同时把有门的那段推出 `fogFar` 之外。

### 逐条排除的「不是原因」（这轮做了 6 组探测）

- **不是分段隐藏** —— `SegmentVisibilityWrapper` 全程 `visible: true`（上一轮的修复有效）
- **不是背面剔除** —— 所有门 `culledNow: 0`，`facing` 均为正
- **不是状态卡死** —— 上下文全程正常
- **会恢复** —— 退到 z=57.6 时 `drawn: 0`，再前进到 z=28.1 时 `drawn: 2`

### 空间模型的真相（与用户对齐时发现的更大问题）

用户问「进大门之后廊道是不是首尾相接的无限循环空间？」——**一半对**：

**✅「无限延伸」成立**：`InfiniteCorridorManager` 按相机 z 程序化挂载
`[current−1, current, current+1]`，**双向**生成；每 80 单位一扇大双开门
（`SegmentDoors`）在**所有**分段都有 → 「无穷走廊」的观感成立。

**❌「首尾相接」不成立**：全库**没有任何 wrap / z 重置逻辑**。
`targetZ -= delta` 无界，`camera.position.z = currentZ.current` 直写。
往回走不会回到起点，两个方向不对称。

**❗最关键的落差**：房间门是**硬编码的两组**——

```js
const definitions = segmentIndex === 0 ? FIRST_RUN
                  : segmentIndex === 1 ? SECOND_RUN
                  : [];          // ← 其它分段：0 扇门
```

- 段 0（z 10…−70）：档案 / 摄影 / 工作室 / 文稿
- 段 1（z −70…−150）：视频 / 音乐 / AI+ / 联系
- **段 −1（z 10…90，相机出生地）、段 −2、段 2 起：一扇房间门都没有**

所以真实形态是：**一条双向无限延伸的走廊，8 个房间全部集中在前进方向的头两段**。
用户的心智模型（循环）与实现（单程 + 两端空）不一致 —— **这个落差就是 bug 的本质**。

**有力旁证**：`LoopDoors.jsx` 里写着 `creating an infinite loop illusion`，
且它**从未被任何地方 import**（全库搜索为零）→ 真·首尾相接是**设计过但没接上**。
说明用户的心智模型其实就是**最初的原始设计意图**。

### 待用户拍板的三个方向

1. **给相机加后退边界**（最小改动，`targetZ` 钳到刚进屋附近）
2. **让雾别抹掉门**（给门/门框关 fog，或提高 `fogFar`；与装饰处理保持一致）
3. **补上循环**（段 −1 起也有房间门，走廊真正首尾相接 —— 即把 `LoopDoors` 的意图做完）

我的建议是 1+2 先做（保证「只要门在视野里就一定看得见」），3 作为设计决策单独谈。

### ✅ 用户一句话点破了关键：**廊道每 80 单位完整重复一次，连 ZEO 一起重复**

用户观察：「进了 z=15 的双开门，看到了 z=7.7 的人；往后退，退出的门似乎变成了 −65 的门；
若往前走跨过门，又看到了 7.7 的人 —— 所以给我一种无限循环的幻觉。」

实测清点（`window.__scene` 遍历，同一时刻）：

| 相机 z | 场景里的 ZEO |
|---|---|
| 28 | **167.7 · 87.7 · 7.7** |
| −1.8 | 87.7 · 7.7 · **−72.3** |
| 28（退回后） | **167.7 · 87.7 · 7.7** |

**3 个人同时存在，间距正好 80 = `SEGMENT_LENGTH`。**

原因：`Avatar` 挂在 `CorridorSegment` 里的
`<group position={[0, 0, zOffset - 2]}>`（`CorridorSegment.jsx:70`），
而 `InfiniteCorridorManager` **双向**挂载 `[current−1, current, current+1]`
→ **每个被挂载的分段都有自己的人、自己的 HeroText、自己的地贴、自己的 Doodles、
自己的 SegmentDoors**。

完整坐标表（代码推导 + 实测一致）：

|---|---|---|

用户报的 **15** 和 **−65** 与代码完全吻合 —— 他的空间感是准的。

### 这让「无限循环」这件事变成**成立的、但只做了一半**

**✅ 已经循环的**：墙、地板、天花板、装饰、**人 ZEO**、分段大门 —— 全部每 80 单位重复
→ 这就是「无限走廊」观感的真正来源。用户每次跨过分段大门，前方 ~7 单位处必然出现一个人。

**❌ 没有循环的**：**房间门**。它是硬编码的两段：
```js
segmentIndex === 0 ? FIRST_RUN : segmentIndex === 1 ? SECOND_RUN : []
```
8 个房间全挤在段 0 和段 1，段 −1 / −2 / 2 起 **一扇都没有**。

→ 所以「往后退」= 退进一段**有画面节奏、但没有目的地**的走廊；
再叠加雾（`fogFar 60`），段 0 的门也被抹掉 → 「房间全没了」。

**结论：视觉节奏在循环，目的地不循环。这个不一致就是 bug 的本质。**

### 待拍板（这次结论更明确了）

因为**场景已经在循环**，最自然的修法是把「房间门也纳入循环」：
让每个分段都带同样的门（或至少让房间分布与 80 单位周期对齐），
这样无论前进还是后退都永远看得到房间。

备选是「承认不循环」：给相机加后退边界 + 门关雾效，把用户限制在有房间的区间里。

两者都要先解决「门被雾抹掉」。等用户定。

### ✅✅ 用户给了 4 张截图走完整个复现 —— 空间 A / 空间 B 映射已确认

用户五步复现（配 4 张截图）：

## 走廊「真环」改造：房间纳入循环（Part L）

**用户诉求（原话）**：「我觉得真正的循环应该是让空间A和B首尾相接，我不用管这两个空间是否有房间。按照真实的循环感觉去做」

### 根因（此前已查明，此处落地）
走廊环境**本来就是周期性的**：墙、地板、天花板、墙上挂画/通风口、涂鸦、
带∞画的双开门（SegmentDoors）、甚至 ZEO 本人，全部只由 `zOffset` 定位，
因此每 `SEGMENT_LENGTH = 80` 单位**完全重复**（见 `CorridorDecorations` 连 `segmentIndex`
都没接收）。**唯一的例外是房间门**：

```js
// 旧代码（CorridorSegment.jsx）
segmentIndex === 0 ? FIRST_RUN : segmentIndex === 1 ? SECOND_RUN : []
```

于是 8 个房间只存在于「进门后的两段」里，之后的走廊**视觉上无限循环、目的地却用完了**。
再叠加 `fogFar = 60`（装饰物是 fog-off 的 basicMaterial，门是普通 fogged 材质），
走远后连仅剩的门也被雾抹掉 → 用户看到的「装饰还在、门全没了」。

### 改动（CorridorSegment.jsx）
```js
const LOOP_SPACES = [FIRST_RUN, SECOND_RUN];
// 用取模索引代替硬编码比较——这一步就是「闭环」
const loopIndex = ((segmentIndex % LOOP_SPACES.length) + LOOP_SPACES.length) % LOOP_SPACES.length;
const definitions = hideSegmentDoors ? [] : LOOP_SPACES[loopIndex];
```
- 同时把地上的 `AISPIN · 0n` 标签也改用 `loopIndex`（否则 seg≥2 会「有装饰、没编号」，
  看起来像 seg0 的残缺克隆）。
- `hideSegmentDoors` 复用为「这是屋外」的信号（seg −1）。

**结果：周期 160 单位**。seg0/2/4…= 空间A（about/gallery/studio/posts），
seg1/3/5…= 空间B（videos/music/ai/contact）。实测 seg2 出现「档案」、
seg3 出现「视频」，与空间定义一致。

### 连带修掉的隐患：`pendingDoorClick` 按固定段号匹配
`DoorSection.jsx` 里原来是：
```js
const expectedSegment = ['videos','music','ai','contact'].includes(doorId) ? 1 : 0;
```
房间重复挂载后（管理器常驻 3 段，同一房间会同时存在两份），这段逻辑既会**漏**掉
其他副本、又可能在**错误的副本**上触发。改为**用相机实时所在段**判定：
```js
const cameraSegment = Math.floor((10 - camera.position.z) / segmentLength);
const isTargetDoor = segmentIndex === cameraSegment;
```
新增 `segmentLength = 80` prop（由 CorridorSegment 传入）。

**为什么安全**：`TeleportRoom.jsx` 在把相机移到 `doorZ + 8` **之后**才
（`setTimeout 50ms`）调 `completeTeleport()` → `setPendingDoorClick()`，
所以 effect 跑的时候相机已经就位。已用算术逐条验证 8 个房间
（about→seg0 … contact→seg1）全部匹配，无一处错位。

### 验证（headless，`?noloader=1`，SwiftShader）
| 相机 Z | 段 | 雾内可见门 | 截图确认 |
|---|---|---|---|
| 0 | 0 | 12 | 档案 |
| −80 | 1 | 16 | （空间B）|
| −160 | 2 | 12 | **档案（空间A 重现）** |
| −240 | 3 | 16 | **视频（空间B 重现）** |
| −320 | 4 | 12 | （空间A 再次）|
| −160（从 −320 往回走）| 2 | 12 | 门仍在 |
| 0（绕一圈回来）| 0 | 12 | **档案仍在** |

→ 原 repro「往后退房间消失」已修复；来回走一圈房间不丢。
另外点击 seg2 的门 → `currentRoom: "gallery"`；`teleport('videos')` → `currentRoom: "videos"`。

### 性能
门贴图（`doorArt.js` / `corridorArt.js`）都是**按 key 缓存**的，
所以重复的段只重复 mesh/geometry，不重复贴图。每 3 段 24 个可点 mesh（其中 12 个是门）。

### 探测方法上的两个坑（已补进 skill）
1. **不要用 `rAF` 死循环覆写 `camera.position`**：`useInfiniteCamera` 的 `useFrame` 同帧还会再写，
   导致「读到的 Z 是 A、渲染出来的是 B」。要走应用自己的 `wheel` 事件通路。
2. **按几何特征找物体要先打印特征自证**：门宽真值 `2.5*0.376*1.12 = 1.0528`，
   我按 `1.05±1e-6` 扫 → 0 个。改用 `o.__r3f.handlers.onClick` 判定更稳，
   还能顺便排除墙上挂画（画的 hitbox 用 `frame.width/height`）。
   另外 `evalClick` 回调**必须恰好返回 `[x,y]` 两个元素**，多带一个就被 SKIP。

### 更正：`.preloader` 并**不会**残留成隐形点击拦截层
此前记过一条「Preloader 退出后仍留在 DOM（display:block / opacity:0）且没设
`pointer-events:none`，是一个全屏隐形点击拦截器」。**这条是错的，撤回。**

实查 `Preloader.jsx:353`：退出动画的 `onComplete` 里 `setIsDone(true)`，
而组件体开头就是 `if (isDone) return null;` —— 退出后**整个卸载**，不会残留。

之所以会误判：测量时 preloader 还**没加载完**（SwiftShader 下 30 s 时仍
`display:block / opacity:1`，`elementFromPoint` 命中的是 `preloader__half--left`），
把「加载中」误读成了「退出后残留」。**教训：判断「某覆盖层是否残留」前，
先确认它已经走完退出流程**（读它的 `isDone` / 相关 state，或等到 `isLoaded` 为真），
否则测到的是加载态。
