## 0. 一句话结论

Tidewater 是一个**自研 WebGPU 引擎**写的海岛钓鱼游戏（209 个 js/wgsl 源文件、**80,899 行**、
**零运行时依赖** —— 连 three 都删掉了，只有 `vite` + `webgpu` 两个 dev 依赖）。
它的渲染管线、程序化美术、音频组织、测试与性能工具链**都很成熟**，
但**代码几乎不能直接搬**：语言是 WGSL，运行在 WebGPU，宿主是它自己的引擎。

**能搬的是四类东西**：① 纯数学/纯公式（可直接翻译成 GLSL/JS）；② 管线顺序与默认参数（拿来就能用）；
③ 工程做法（测试门、基准、功能开关）；④ 反面清单（哪些看起来香但对我们不划算）。

## 2. 逐条可落地清单

分档标准：**P0** = 零新依赖、可当天落、风险低；**P1** = 需要一个决策（通常是"要不要引入后处理链"）；
**P2** = 代价大 / 要动架构，先记着。

### P0 — 零新依赖，直接可用

#### ① 程序化星空 / 月 / 银河 —— 最契合我们的一条
- **他们怎么做**（`src/sky/Sky.js:98-155`）：
  - 星：把天球按**立方体面**切成网格（`STAR_CELLS=160`/半面），每格一个候选星，格内抖动位置；
    星等用**幂律分布**（`m = log2(u)*0.602 + 6.5`，亮星少暗星多）；亮度按**银河带**加权
    （`band = exp(-(dir·MW*4)²)`）；PSF 用高斯，亮星"看起来更大"；
    闪烁 `sin(time*(h*9+5)) * mix(0.18,0.06,sat(dir.y*2))`；地平线消光 `smoothstep(0,0.2,dir.y)`；
    银河弥散辉光 + 星的颜色按 hash 在暖白/冷蓝之间取。
  - 日轮：`smoothstep(1.0,0.9,ang/0.004675)` + **边缘变暗** `1-0.6*(1-mu)` + 大气透射率。
  - 月：半径 0.0048 rad 的圆盘 + `exp(-ang*14)*2.4 + exp(-ang*2.5)*0.9` 的**月晕**。
  - 夜空底色是**极暗**的蓝灰（`vec3(0.005,0.0068,0.0105)`）——不是纯黑。
- **我们怎么落**：`WeatherLayer.jsx` 已经是"挂在相机前的全屏平面 + 自定义 fragment"（`DIST=2.6`、
  `renderOrder=999`、`depthTest:false`），**星空就是同一个套路**：往 `天象` 那一层再加一个
  `uStars` 分支，或者单独一层晴天专用的夜空层。全部程序化、零贴图，**完全符合我们的美术纪律**。
- **为什么值**：我们现在"夜间/晴天夜空"信息量偏低，这是**纯加法**（新代码，不动现有机制）。
- **判据**：横竖两种视口都拍（`shot-weather.mjs` 已是双视口）；星点不得有方块/闪烁抖动感；
  关掉 `uStars` 时与现在逐像素一致。

#### ② 镜头水珠（雨天）—— 性价比最高的一条
- **他们怎么做**（`src/post/LensDroplets.js:67-158`，158 行）：**两层**雨滴网格（小滴 `cell=0.05` 黏附、
  大滴 `cell=0.13` 延迟后下滑并留**湿痕**）；每滴是**各向异性抖动的轮廓**（3/5 次谐波）；
  滴内是**模糊且倒置**的场景成像（`lensBlurred(uv + n2*-0.05)`）、强天空高光、暗边；
  蒸发让它随时间缩小（`r *= sqrt(life)`），9 秒干（`duration=9`）。
  三层 hash 全在 shader 里（pcg2d 整数 hash，不用三角函数）。**零贴图、零依赖。**
- **我们怎么落**：我们**已经有雨**（`useWeather` → `weatherLevels()` → `uRain`，
  `shaders/entranceTextures.js` 的 `uSnow/uRain` 同层合成）。水珠挂在`天象平面`同一层即可，
  强度直接跟 `uRain` 走，另加"雨后 N 秒渐变干"。
  没有后处理链也能做 —— 它就是"相机前的一张全屏透明平面"，我们这条通路已经跑通了。
- **判据**：`uRain=0` 时 0 开销（一致分支）；雨强度变化时水珠密度跟随；竖屏不变形（除 aspect）。

#### ③ Bayer 有序抖动交叉淡入 —— 治"一帧切换"
- **他们怎么做**（`src/materials/LODFade.js:21-50`，50 行）：过渡带内**两层都画**，
  各自用 **Bayer 4×4** 阈值 discard：进来的保留 `t < fade` 的像素，出去的保留 `t >= fade` 的像素，
  **同一个阈值** ⇒ 合起来恰好覆盖每个像素一次（无洞、无重画）。图案**每帧位移**（`f*3`），
  由 TAA 把 16 级抖动解析成平滑过渡。
- **我们怎么落**：我们场景里所有"出现/消失"都是硬切：雨雪层淡入、荷花缸外移、花箱随季、
  房间预热、走廊远端淡出。**纯 GLSL 十几行 + 一个 `bandFade(dist,start,end)` 的 JS 工具**。
- ⚠️ **诚实标注限制**：他们能吃这招是因为**有 TAAU**；我们**没有时间抗锯齿**，
  逐帧位移的 4×4 图案会**闪**。所以两个选项：
  (a) 图案**不逐帧位移**（静止抖动，肉眼几乎看不出，代价是 16 级台阶是固定的）；
  (b) 先在 P1 把 TAA 建起来，再上位移版。
  **建议先做 (a)**：一次性 16 级淡入已经远好过现在的硬切。
- **判据**：同季 A/B 截图；淡入过程中不得出现"半透明变暗"（两层叠加错配的症状）。

#### ④ URL 功能开关 —— 直接改善我们的排查与截图
- **他们怎么做**：`App.js:82` 建 `URLSearchParams`，之后每个子系统一行判断：
  `?noClouds`（`App.js:117`）、`?noHaze`（:329）、`?noCaustics`（:183）、`?noSim`（:186）、
  `?noVeg`（:143）、`?noAudio`（:340）、`?fly`（:317）、`?scale=0.7`（:335）；
  `main.js:7-32` 另有 `?bench`、`?auto=`、`?shots=`、`?wdbg=`；`core/Profiler.js:20` 有 `?profile`。
- **我们怎么落**：我们已有 `?season=` 先例。补几个**排查/截图用**的：
  `?noWeather`（跳过雨雪层）、`?noAudio`（静音启动）、`?dpr=0.75`、`?t=`（冻结时间/固定 clock）。
  **收益在 harness**：截图脚本的可复现性会明显变好（现在是靠 `sessionStorage` 注入 + 预热页）。
- **判据**：带参启动一次，控制台打印生效的开关表；默认（无参）行为逐像素不变。

#### ⑤ 太阳位置模型（3 行公式）
- **他们怎么做**（`src/sky/Sky.js:258-268`）：`sunDirectionFromTime(hours, latitude, declination)`
  → 标准时角公式，返回世界系太阳方向。他们默认 `lat=24°, dec=6°`。
- **我们怎么落**：天象现在是**按真实预报**驱动（§10），但太阳高度角/方位角若是按季节写死的，
  换成这个函数就能"真实的冬夏日照角度"。三行数学，零成本。
- ⚠️ 先确认我们现在的太阳角度**是不是**已经由季节表驱动（`config/seasons.js`）——如果是，
  这只是"表 vs 公式"的替换，属于可选优化，不是必须。

#### ⑥ 照片模式（P）
- **他们怎么做**（`src/ui/UI.js:3116-3156`）：一个 `_photo` 标志 ⇒ 隐藏全部 UI，
  只留一个 2.4 秒后自动消失的"按 P 退出"提示；`localStorage` 记住上次的 tab。
- **我们怎么落**：我们的 UI 已经是 DOM 覆盖层（`GlobalOverlay` / `NavigationUI` / `SiteControls`），
  加一个布尔 + CSS class 即可。**照片模式 + 我们的 `harness/shot-*.mjs` 是天然搭配**。
- **判据**：进入照片模式后 DOM 里不留任何可见元素；退出后恢复原状。

#### ⑦ `npm test` 入口 —— 把已有的 112 个 harness 收进一个门
- **他们怎么做**：`package.json` 里 `"test": "node test/game-logic.mjs && node test/engine-smoke.mjs"`。
  `engine-smoke.mjs` 用 `webgpu` npm 包**无头起 GPU**，渲一帧、`writePNG()` 落盘、打印绘制统计；
  `game-logic.mjs` 是**纯逻辑断言**（无 GPU）：本地 LCG 随机数、逐条 `ok(cond, msg)`、末尾计数失败。
- **我们怎么落**：我们 `.workbuddy-ai/harness/` 已有 112 个脚本（含 `imgdiff.py`、`compare-two.py`），
  但**没有统一入口**。建议：把**纯函数/断言类**的挑出来（`weather-levels-test.mjs`、`check-sw-dev.mjs`、
  `music-mute-check.mjs`…）合成一条 `npm test`，断言风格照抄"`ok()` + 失败计数"（够用，零依赖）。
- **判据**：`npm test` 全绿；故意改坏一个断言能红。

### P1 — 需要一个决策（基本都是"要不要建后处理链"）

#### ⑧ 最小全屏后处理（tone map + vignette + grain + 输出 dither）
- **他们怎么做**（`src/post/PostFX.js:458-543` 是最后一 pass，参数默认值在 `:73-82`）：
  - **ACES filmic**（three 的拟合曲线，`PostFX.js:36-57`）—— 他们连 tonemap 都是在 shader 里手写的；
  - 后面依次：`warmth` 白平衡微调 → `saturation 1.06` → 以中灰 0.18 为锚的 `contrast 1.04` →
    椭圆柔和**暗角 0.28** → **亮度加权胶片颗粒 0.012**（三角白噪，**每帧换图案**，因为"固定图案在暗部
    会出现斜向网纹"）→ **±1 LSB 三角抖动**后才输出 8 bit（**专门治天空渐变色带**）；
  - 另有 **RCAS 锐化**（AMD FSR1，`:480-499`）——只用来补 TAA 的软化，且**天空只锐化 30%**
    （"云的采样噪声会被锐化成细颗粒"）。
- **我们怎么落**：我们目前**没有任何后处理**（`package.json` 无相关依赖，`App.jsx` 未设 `toneMapping`，
  全站 `shadows={false}`）。建议**只做最小一档**：
  **一个全屏 pass = ACES + vignette + grain + 输出 dither**（四件事一次 draw，零新依赖，自己写 GLSL）；
  bloom 独立评估。
- **重点**：**输出 dither 可能直接治好我们天象/夜空/雾的色带**——这是"看得见的收益"。
- **DR（需要用户拍板）**：是否引入 `postprocessing`（pmndrs）依赖？我倾向**不引入**：
  自写一个全屏 pass 只有约 60 行 GLSL，而依赖会带进一棵不小的树、且和我们的
  "材质/uniform 必须怎么改"纪律（§9.4i）多一层耦合。
- **判据**：同季 A/B 逐像素（`imgdiff.py`）；天空渐变处色带消失；grain 在静态截图下不刺眼；
  关掉后与现在逐像素一致。

#### ⑨ 自动曝光（眼适应）
- **他们怎么做**（`src/post/PostFX.js:85-96` 参数、`:394-455` 实现）：
  从 **1/16 缩放级**取景 → 单 workgroup 256 线程归约 **log2 亮度**（中心加权）→
  `ratio = refLum/avg`，**只部分补偿**（`pow(ratio,0.8)`，怕夜景被拉成白天）→
  目标夹在 `[0.6, mix(6.0, 2.0, night)]` → 用**不同速率**指数趋近（亮起来 1.6/s、暗下去 1.1/s）。
- **我们怎么落**：我们没有 GPU compute，但**根本不需要**：每 15~30 帧把画面 downsample 到 8×8、
  `readRenderTargetPixels` 读回、CPU 上算平均亮度 → 更新一个 `uExposure` uniform。CPU 成本可忽略。
- **为什么值**：我们已经有**四季光照 + 夜间模式 + 雨天**，同一套材质要在"冬日正午/夏夜/雨天"都不糊，
  自动曝光是最省事的统一手段（比逐季手调 12 套曝光参数便宜）。
- **判据**：四季 × 昼夜拍一遍定妆照，逐张看"过曝/发灰"；切换季节时曝光变化必须是**渐变**不是跳变；
  `prefers-reduced-motion` 下关掉适应。

#### ⑩ 局部灯光池（灯笼 / 窗光 / 手电）—— 对我们"夜间模式"最有价值
- **他们怎么做**（`src/materials/LocalLights.js:8-40`）：**不为每盏灯建一个光源对象**，
  而是 CPU 每帧挑**最近的 8 盏**打进 3 个 uniform 数组（每盏 `pos.xyz+range²`、
  `col.rgb+强度+内锥cos`、`dir.xyz+外锥cos`），**每个被照材质在一个循环里算完**
  （物理 BRDF：漫反射 + GGX 高光，平方反比 + 平滑范围窗 + 可选聚光锥，**不投影**）；
  白天无灯时循环上界为 0，整个跳过。带 `NO_LOCAL_LIGHTS` / `LOCAL_LIGHTS_CHEAP` 材质开关。
- **我们怎么落**：我们的夜景现在是"整体变暗 + 环境色"，灯笼/窗纸是**自发光但照不亮周围**。
  这套"最近 N 盏 + uniform 数组 + 材质内一个循环"完全可以在 three/R3F 里复刻
  （自定义 shader 材质本来就有；8 盏灯的循环在 fragment 里很便宜）。
- **判据**：夜间定妆照里，灯笼附近地面/墙面有可辨的暖色衰减；白天 0 额外开销；
  长廊只允许最多 N 盏灯参与（用 `probe-*` 测 uniform 数量与帧时间）。

#### ⑪ 屏幕空间 god rays / 高度雾
- **他们怎么做**（`src/post/AirHaze.js`，606 行，结构在 `:13-49`）：两层指数高度雾
  （海面薄雾 `sigma=1.5e-4,H=110` + 高空气溶胶 `3.2e-5,H=1400`）解析求光学深度，
  雾色取"该方向地平线上方一点的真实天空色"（所以远景是真的融进天空）；
  体积光轴：**半分辨率 16 步 march**（吃级联阴影 / 地形影 / 云影）+ 逐像素逐帧抖动 + 时域累积；
  **再叠一层屏幕空间 god rays**（`GPU Gems 3 ch.13` / UE4 做法：四分之一分辨率、
  朝光源屏幕位置做 3 遍 × 8 tap 径向模糊 = 512 有效采样，`:42-45` 有 3 个衰减常数）。
- **我们怎么落**：我们的"门口逆光""走廊晨光""雨天灰雾"正是它的用武之地。
  **先做屏幕空间那一半**（不需要阴影贴图，只要"亮部掩码 + 径向模糊"），
  成本是 2~3 个低分辨率 pass。依赖 ⑧ 先建好后处理链。
- **判据**：横竖双视口；光轴在移动相机时**不抖动**（抖动必须由累积/降噪吸收）；关掉后逐像素一致。

#### ⑫ 音频：LUFS 目标混音 + 事件驱动 + 并发上限
- **他们怎么做**（`src/audio/SoundScape.js`，1,416 行，文件头 `:1-33` 有完整信号流图）：
  - **每个声音一个"目标响度"（LUFS）**写在 `MIX` 表里（`:51-99`，例如
    `crash(破浪 10m) -15`、`wind -36`、`step(脚步) -56`、`whaleSong -26`）；
    实际增益 = **目标 LUFS − 该音频文件实测 LUFS**（`soundBank.js` 里存的）。
    ⇒ **不管素材录得多响多轻，场景里的相对关系是对的**。
  - **逐类并发上限** `LIMITS`（`:117`，`crash:7`、`step:3`、`whale:4`…），超了就把最老的淡出。
  - **事件驱动 one-shot**：破浪声是**逐波**触发的 —— CPU 侧复刻了岸浪的相位场 + 沿岸一排
    9 个监听站（`:122-123`），波到达时在**发生的位置**起一声 HRTF 化的碎裂声；
    鸟叫按**树上的随机栖枝 + 时段**（黎明合唱 / 中午停顿 / 夜里静音）；鲸只在 100m 内可闻。
  - 分组总线 + 水上/水下两套滤波 + 末端安全限幅器。
- **我们怎么落**：我们的 BGM/环境音是**生成式**（`audio/bgm.js`、`ambience.js`），没有素材响度问题，
  但**两条可以直接借**：
  (a) **`MIX` 表思路** —— 给每个音源一个**相对的"目标响度 + 参考情境"**（如
  "风铃：无风时听不见；3 m/s 时约为环境音的 -12 dB"），全部走 `dB→线性` 换算，不再靠手调魔法数；
  (b) **事件驱动** —— 雨声强度跟 `uRain`、雪落跟 `uSnow`、风铃跟风速、狗叫/燕子在"它真的在那里"时响。
  我们已有 `engine/audioBus.js` 的**全站唯一 AudioListener** 和 SpatialSfx，位置化这一块是现成的。
- **判据**：`harness/audio-check.mjs` / `music-mute-check.mjs` 扩展：断言"雨强度 0 时雨声源 `audible===false`"、
  "并发不超过上限"；人耳验收各季节声床。

#### ⑬ 逐 pass 计时 + 固定机位基准
- **他们怎么做**：
  - `core/Profiler.js`（137 行）：`?profile` 打开，包装每个 pass 写 GPU timestamp，
    异步读回，输出 `{ compute, render, items:[{name, ms}] }` **按耗时排序**；
  - `core/Bench.js`（332 行）：`?bench` 停掉渲染循环，**固定输出尺寸 2560×1267**、
    **固定 8 个机位**、**预热 90 帧 + 测 120 帧、`dt` 固定 1/60**（`:234-275`），
    报 GPU/CPU/墙钟 ms + **per-pass 成本 top N**；
    还有 `shots()`（`:284-330`）：**`dt=0` 冻结模拟**（浪/云/粒子/动物全停、时域滤波收敛），
    渲染成**逐位可复现**的参考图，POST 到本地 `127.0.0.1:5190` 收集器，
    "同一份代码给出同一张图，改前改后可以逐像素比"。
- **我们怎么落**：**我们已经有一半**（`.workbuddy-ai/harness/` 112 个脚本 + `imgdiff.py`）。
  值得补的是两件事：
  (a) **固定机位 × 固定 dt 的"参考图"流程**（我们的 `shot-*.mjs` 是"挑好看的角度"，
      基准应该是"永不改的机位 + 冻结时钟"，两张图直接 diff）；
  (b) **基准改为 POST 到本地收集器**而不是往仓库里塞 PNG（避免 `dist-*` 那种堆积）。
- ⚠️ **限制**：WebGL2 没有 WebGPU 的 timestamp-query（`EXT_disjoint_timer_query_webgl2` 普遍不可用），
  所以**拿不到 per-pass GPU 时间**。我们能做的是：CPU 侧 frame time 分位 + `renderer.info`
  的 draw/tri 计数 + 固定机位参考图 diff。**别指望复刻它那张 per-pass 表。**
- **判据**：同一提交连跑两次，参考图逐像素 0 差异；改动后差异集中在预期区域。

### P2 — 代价大，先记着

#### ⑭ 地面反弹光（GroundBounce）
`src/materials/GroundBounce.js`（195 行）：512² 的 RGBA16F 贴图，**太阳一动就重烘焙**，
存"地面每单位太阳辐照度反射出去的辐照度"（地表反照率 × cos × 高度场自阴影 − 环境贴图已有部分），
5×5 二项式模糊；着色时按 `view = (1-N.y)/2`（下半球视图因子）+ 离地高度衰减加进间接漫反射。
**对我们的意义**："石板太白""夜里物体没有落地感"这两个老问题，正是缺反弹光/接触阴影的症状。
但我们要么得**开阴影系统**（现在是全站 `shadows={false}`，README 里明确写着这是性能决策），
要么退化成"一张程序化径向渐变的假接触阴影贴片"。**倾向前者里的"假贴片"**：我们画程序化贴图的
能力是现成的，成本接近 0，收益是"东西落在地上"。

#### ⑮ 逐材质 AO（GTAO）
`src/post/GTAO.js`（357 行）+ `PostFX.js:104-175` 的接线：**半分辨率**（且随分辨率缩放一起降）、
在**深度重建的法线**上做 12 tap 地平线搜索、**时域旋转过滤**、再做 **5+5 分离式深度感知降噪**
（"GTAO 的方向在 5×5 上旋转、步长逐像素逐帧抖动，只有时域能平均掉；在摇动的驾驶台上
它噪得像闪"）、半分辨率结果的**深度感知 4 抽样上采样**（避免深度边缘的暗晕）、
最后叠 **Jimenez 2016 多次反弹近似**，并且**只削弱环境光**（"被太阳直照的表面只吃 1/3，
既接地又不脏"）。对我们：走廊/房间的角落确实缺这块，但这是"必须先把后处理链 + 深度
搞对"的活，属大改。

#### ⑯ 时间抗锯齿 / 超分（TAAU）
`src/post/TemporalUpscale.js`（650 行）+ `PostFX.js:185-193`：jitter 相机 + 速度缓冲 + 历史累积 +
**RCAS 锐化**回补；另有 SMAA/FXAA/`smaataa` 三档替代。**这是"便宜的抗锯齿 + 内部降分辨率"的正路**，
也是 ⑨⑩⑪ 那些抖动噪点能被消掉的前提。但我们（R3F + WebGL）要复刻，等于自己写一个
velocity buffer 和一个历史重投影 —— 工作量以"周"计。**结论：不主动上，除非日后被锯齿逼到。**

## 5. 一处勘误 —— 以及顺手核了一下我们自己的降级

README 写 "dynamic resolution scales the render down on slower machines"，
但源码里 **render scale 是手动的**：`App.js:704-713` 的注释明确写
"*set by hand: changing it re-creates the scene / post / cloud targets, so nothing adjusts it automatically*"。
UI 里只有一个 `Render scale` 滑杆（0.5~2，`Engine.resize()` 拿它当 DPR 用，`Engine.js:58-71`）+
Low/Medium/High/Ultra 预设 + 一个**硬编码**的 "Apply recommended" 按钮（`UI.js:3494-3502`）。
⇒ 这一句 README 不能照抄当事实。

**我们的现状**（顺手核实，结论是我们在这一点上其实更强）：
`context/PerformanceContext.jsx:59-91` 启动时按 `userAgent` / `hardwareConcurrency` /
`deviceMemory` 定 HIGH|MEDIUM|LOW；每档给 `dpr` 区间、`antialias`、`particleCount`、`textureQuality`；
`App.jsx:239-242` 挂着 drei 的 `<PerformanceMonitor onDecline={downgradeTier} onFallback={…}>`，
**帧率下降时会真的降档**。

**唯一比它弱的地方**（如果要补，是一小步）：我们的降档是**单向的**（HIGH→MEDIUM→LOW，不回升），
且 dpr 是**每档固定的区间**，不随帧时间连续微调；它那边虽然要手动，
但 `renderScale` 是**连续值**（0.5~1，步进 0.05）并且可以走 URL（`?scale=0.7`）。
⇒ 可选的小改进：给 HIGH 档加一个 ±0.05 步进的连续 `renderScale`，并允许**回升**。
