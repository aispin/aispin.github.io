# Web 3D 实战及技术拆解：从一座黄昏小院说起

> 以“老房子、柿子树、石桌、祖孙三人、一只小狗、门内透出的黄光”为例，完整走一遍 Web 3D 的技术选型、场景拆解、代码落地与结构层级的坑。

## 一、为什么选这个场景

一个黄昏小院，几乎把 Web 3D 的所有难点都集齐了：

- **自然环境**：黄昏天空、雾、暖色光照、长影子
- **程序化植被**：柿子树的枝干递归生长、叶子与果实的风动
- **建筑与物件**：老房子的几何体、圆石桌的材质
- **角色**：两个老人和一个孙子，需要姿态但不需要高精度骨骼
- **动物**：一只小狗，需要简单的运动
- **特殊光照**：门内透出的黄色灯光，照在石桌后面，形成暖色光锥
- **氛围粒子**：黄昏里可能有的萤火虫或尘埃

这个场景做完，Web 3D 的核心能力基本就全覆盖了。

而且——它还额外教会了我们**最重要的一课**：**3D 场景的复杂度，从来不来自几何体数量，而来自层级关系。**

## 二、技术选型总览

先给结论，再拆细节：

| 技术 | 在本场景中的职责 |
|---|---|
| **Three.js** | 场景主框架：几何、相机、光照、阴影、雾、渲染循环 |
| **GLSL** | 黄昏天空、门内光晕、风吹树动、萤火虫闪烁 |
| **Canvas 2D** | 程序化生成黑瓦纹理（CanvasTexture） |
| **SVG** | 页面上的图标、标题装饰、控制按钮 |
| **CloudBase 云函数** | 如果上线，负责登录、分享、场景配置同步 |

一句话：**Three.js 搭骨架，GLSL 注入灵魂，Canvas 生成材质，SVG 负责皮相。**

## 三、场景拆解

### 3.1 黄昏天空——用 GLSL 写一个渐变球

不要用贴图。黄昏天空用 `ShaderMaterial` 写一个球体，从地平线的暖橙过渡到天顶的深蓝紫，再叠一层太阳光晕。

```glsl
// fragment
varying vec3 vWorldPos;
uniform vec3 uHorizon;   // 暖橙
uniform vec3 uZenith;    // 深蓝紫
uniform vec3 uSunDir;
uniform vec3 uSunColor;

void main() {
  vec3 dir = normalize(vWorldPos);
  float h = clamp(dir.y * 0.5 + 0.5, 0.0, 1.0);
  vec3 sky = mix(uHorizon, uZenith, pow(h, 0.8));

  // 太阳光晕
  float sun = pow(max(dot(dir, uSunDir), 0.0), 32.0);
  sky += uSunColor * sun * 0.8;

  gl_FragColor = vec4(sky, 1.0);
}
```

配合 `ACESFilmicToneMapping`，整个画面的暖度会自动收敛，不会过曝。

### 3.2 老房子——从几何拼装到层级重构

这是整个场景里**最难、也最有教育意义**的部分。我会把完整的踩坑过程写出来，因为这一段的价值远超代码本身。

#### 3.2.1 初始方案

老房子的第一版是这样拼的：

```text
屋体（Box）：4.2 × 2.7 × 3.0
屋顶（两坡 PlaneGeometry）：4.8 × 3.4，屋脊高 1.5
山墙（ExtrudeGeometry 三角形）：挤在 ±bodyW/2
搏风板（BoxGeometry 木条）：压在屋顶斜边
```

看起来没什么问题。但一渲染，问题就来了：**搏风板浮在瓦面上**。

#### 3.2.2 八轮迭代的血泪史

我试着用八种方法去修搏风板：

| 版本 | 尝试 | 结果 |
|---|---|---|
| 1.0 | 搏风板贴山墙外表面 | 屋顶侧切面裸露 |
| 1.1 | 搏风板加厚到 0.22 包住屋顶 | 更厚 → 更浮 |
| 1.2 | 搏风板变薄 0.05 后移 | 还是浮 |
| 1.3 | 用 `quaternion.setFromUnitVectors` 对齐斜边 | 方向对了，位置还错 |
| 1.4 | 沿法线嵌入屋顶 -0.03 | 一半嵌入，一半还露 |
| 1.5 | 移到屋顶外边缘之外 | 从俯视看不到，从侧面还飘 |
| 1.6 | 移除搏风板，让山墙挤出变厚 | 山墙伸出屋顶外，两条黑带 |
| 1.7 | 侧墙做成从地面到屋脊的完整墙体 | 仍然会穿透 |

**每一次“修复”都在制造新问题。**

#### 3.2.3 根因：不是几何问题，是层级问题

直到第 8 版，我才真正意识到问题不在搏风板。问题在**结构层级**：

```text
        屋顶（最高层，Y = 2.7 → 4.2）
              ↓
        墙顶（中间层，Y = 0 → 2.7）
              ↓
        地面（最下层，Y = 0）
```

**任何下方结构的投影，都不能落到屋顶上方。** 这是硬规则。

回头看，之前所有版本都在违反这条规则：

- **`eaveFront` / `eaveBack` 屋檐封条**：Y 位置 `eaveY - 0.02 = 2.68`，高度 0.08 → **上表面在 Y = 2.72，穿透屋顶底边 Y = 2.7**。这就是两条竖直黑条的来源。
- **侧墙挤出到 `ridgeY`**：侧面在 `±2.4`，和屋顶边缘完全重合，产生 Z-fighting。
- **搏风板**：一个本来就不该存在的物体。

#### 3.2.4 正确解法

**第一原则：屋顶是最高层，它必须完全覆盖下方所有结构。**

```js
// 屋体：Y = 0 → bodyH
const body = new THREE.Mesh(
  new THREE.BoxGeometry(bodyW, bodyH, bodyD),
  wallMat
);
body.position.y = bodyH / 2;

// 侧墙：从 bodyH 到 ridgeY - 0.02（略低于屋脊）
const gableShape = new THREE.Shape();
gableShape.moveTo(-bodyD / 2, bodyH);
gableShape.lineTo( bodyD / 2, bodyH);
gableShape.lineTo(0, ridgeY - 0.02);   // ★ 关键：比屋脊低 0.02
gableShape.closePath();

// 侧墙放在 x = ±bodyW/2（屋体内侧）
// 屋顶边缘在 ±roofW/2（更外）
// 屋顶自然悬出 0.3，把侧墙盖住
```

**第二原则：删掉一切不属于建筑本体的几何体。**

```js
// ✗ 删掉：eaveFront / eaveBack（屋檐封条）
// ✗ 删掉：所有搏风板 BoxGeometry
// ✓ 保留：屋体 + 屋顶 + 屋脊 + 侧墙
```

**第三原则：屋顶边缘的“搏风板”，是视觉读出来的，不是画出来的。**

真实的中式民居里，搏风板就是屋顶边缘的一块薄木条，紧贴瓦面，从俯视几乎看不见。**当你把屋顶边缘处理干净时，观者会自动把那条边缘“读作”搏风板。**

#### 3.2.5 层级验证表

最终方案里，每一层的 Y 范围和 X 范围都被严格约束：

| 结构 | Y 范围 | X 范围 | 穿到屋顶上方？ |
|---|---|---|---|
| 屋体 Box | 0 → 2.7 | ±2.1 | ❌ 不穿 |
| 侧墙 | 2.7 → 4.18 | ±2.1 | ❌ 不穿（< 4.2） |
| 屋顶前坡 | 2.7 → 4.2 | ±2.4 | — 屋顶本体 |
| 屋顶后坡 | 2.7 → 4.2 | ±2.4 | — 屋顶本体 |
| 屋脊 | 4.17 → 4.31 | ±2.46 | 骑在屋脊线上（正常） |
| 门框 | 0 → 2.1 | ±0.65 | ❌ 不穿 |
| 窗 | 1.35 → 2.05 | -1.7 → -1.0 | ❌ 不穿 |

**没有一项穿到屋顶上方。** 问题解决。

#### 3.2.6 从中提炼的三条设计原则

一、**从层级出发，不从几何出发**。先定义“谁是最高层，谁在它下面”，再决定每个几何体的 Y 范围。不要在几何层面反复调参数。

二、**反复调整失败的元素，往往本就不该存在**。搏风板我调了八版，最后发现它只是一个视觉概念，不需要独立几何体。

三、**减法比加法更接近真实**。真实的中式民居屋顶构造极简：两面坡 + 一条脊 + 侧墙。任何额外的“装饰”都会破坏这种极简。

#### 3.2.7 程序化黑瓦纹理

屋顶材质不是贴图，而是用 Canvas 程序化生成的：

```js
function createTileTexture(cols, rows) {
  const cv = document.createElement('canvas');
  const ctx = cv.getContext('2d');

  // 深黑灰底
  ctx.fillStyle = '#0d0d10';
  ctx.fillRect(0, 0, W, H);

  // 逐片绘制瓦片
  for (let y = 0; y < rows; y++) {
    for (let x = 0; x < cols; x++) {
      // 每片瓦轻微色差
      // 上亮下暗的纵向渐变（模拟瓦片弧度反光）
      // 顶部高光（翘边反光）
      // 底部暗边（瓦与瓦搭接阴影）
    }
  }

  // 纵向瓦垄间的暗缝
  // 青苔（越靠坡面下方越密）
  // 斑驳水渍 / 烟熏
  return new THREE.CanvasTexture(cv);
}
```

配合几何层面的瓦垄波纹（在 `PlaneGeometry` 的每个顶点按横向位置做正弦位移），就得到一片会随光照变化的黑瓦。

#### 3.2.8 门内黄光——本场景的灵魂

这是整个画面最关键的照明设计。门开着，黄色灯光从里面打出来，照在石桌后面。

**只需要一盏 `PointLight`。** 不需要额外的光锥 mesh。

```js
const doorLight = new THREE.PointLight(0xffb347, 16, 14, 2);
doorLight.position.set(0, 1.15, -2.45);
doorLight.castShadow = true;
doorLight.shadow.mapSize.set(1024, 1024);
```

我一开始加过一个圆锥形透明 mesh 模拟空气中的光柱，结果它总是会有一部分穿到房外，从侧面看就像一团灰色的锥形投影——**画蛇添足**。

**门内 PointLight 已经足够制造“门里透光”的真实感**：它会打在墙上、石桌上、院子里，形成自然的暖色衰减。额外的光锥几何体只会制造伪影。

**这一条也是"减法原则"的延续**：光照氛围要靠真实光源，不要靠伪造的几何体。

#### 3.2.9 关于搏风板的最终结论

搏风板从第 1 版到第 7 版，经历了位置、厚度、颜色、旋转方式的反复调整，都没能真正解决。最终的方案是：

**不画搏风板。**

真实民居里搏风板是屋顶边缘一块极薄的木条，紧贴瓦面。在 Web 3D 里，只要你：

- 屋顶边缘干净利落（无多余几何体）
- 侧墙从地面延伸到接近屋脊
- 屋顶略微悬出墙体

观者的大脑会自动把那条“屋顶边缘 + 侧墙阴影”的线条读作搏风板。**这不是省略，而是抓重点。**

### 3.3 柿子树——递归生长 + 实例化 + 风动

核心三段：

**递归生成枝干**：从主干开始，每次分叉时随机旋转、缩短、变细，末端挂果。

```js
function grow(start, dir, length, radius, depth) {
  const end = start.clone().add(dir.clone().multiplyScalar(length));
  makeBranch(start, end, radius, radius * 0.72);
  if (depth <= 0) { spawnFruits(end); return; }

  const branches = Math.random() < 0.35 ? 3 : 2;
  for (let i = 0; i < branches; i++) {
    const nd = dir.clone().applyAxisAngle(randomAxis(), angle);
    nd.y += 0.22;  // 向上趋势
    grow(start.clone().lerp(end, 0.72 + Math.random()*0.28),
         nd.normalize(), length*0.7, radius*0.64, depth-1);
  }
}
```

**果实与叶子用 InstancedMesh**：几百个柿子、几百片叶子，压成两个 draw call。

**GLSL 风动**：在 `onBeforeCompile` 里注入顶点偏移，用实例世界位置做相位，产生“一阵风扫过树冠”的效果。

```glsl
vec3 wp = (instanceMatrix * vec4(0.0,0.0,0.0,1.0)).xyz;
float sway = sin(uTime*1.6 + wp.y*1.2 + wp.x*0.7) * 0.5
           + sin(uTime*2.7 + wp.z*1.5) * 0.5;
transformed += uWindDir * sway * uStrength;
```

黄昏时风可以更轻，`uStrength` 调到 `0.02` 左右，只让叶子微微颤。

### 3.4 圆石桌——几何 + 石材材质

石桌用 `CylinderGeometry` 做桌面和桌腿，材质用 `MeshStandardMaterial` 配合程序化噪声：

```js
const stoneMat = new THREE.MeshStandardMaterial({
  color: 0x9a9188,
  roughness: 0.95,
  metalness: 0.0,
});
```

石桌是本场景的视觉锚点，祖孙三人围坐，门内黄光正好从后方打过来，桌面会有一圈暖色边缘光。

### 3.5 祖孙三人——低多边形角色

不需要精细建模。用基础几何体组合，或者用极简的胶囊体 + 球体：

- **老人**：稍矮的胶囊体，头部球体，微微前倾的姿态
- **孙子**：更小的胶囊体，坐在石桌边，腿悬空
- **姿态**：用 `Object3D` 的 `rotation` 调整，不需要骨骼动画

关键是**剪影和位置**：三个人围坐在石桌旁，形成三角形的构图，门内黄光从他们背后打过来，边缘光会让轮廓非常动人。

### 3.6 小狗——顶点动画而非骨骼

一只小狗不需要骨骼系统。用几个几何体拼出身体、头、四条腿，然后用简单的 `rotation.z` 摆动尾巴：

```js
dogTail.rotation.z = 0.7 + Math.sin(uTime * 6.0) * 0.35;
```

小狗可以在院子里慢慢走动，用一条闭合的样条曲线做路径。

### 3.7 萤火虫——GLSL 粒子

黄昏院子里，空气里应该有微小的光点。用 `Points` 加自定义 shader：

```glsl
// vertex
varying float vAlpha;
void main() {
  vec4 mv = modelViewMatrix * vec4(position, 1.0);
  gl_PointSize = uSize * (1.0 / -mv.z);
  gl_Position = projectionMatrix * mv;
  // 闪烁：每个粒子相位不同
  vAlpha = 0.5 + 0.5 * sin(uTime * 2.0 + position.x * 10.0);
}
```

颜色用暖黄，数量控制在 60~120 个，太多了会廉价。

## 四、光照与氛围的整体设计

这个场景的光照不是“打亮”，而是“讲故事”：

| 光源 | 作用 | 参数 |
|---|---|---|
| **天空光** | 黄昏整体环境 | `HemisphereLight(0xffd9a0, 0x3a2e28, 0.6)` |
| **太阳** | 低角度暖光，投长影 | `DirectionalLight(0xffcc88, 1.8)`，位置压低 |
| **门内点光** | 场景灵魂，暖黄 | `PointLight(0xffb347, 16, 14, 2)` |
| **补光** | 从相机侧微微补一点冷色 | `DirectionalLight(0x6688aa, 0.3)` |

阴影只让太阳和门内光投射，其他光源关掉阴影，性能会好很多。

雾用 `FogExp2(0xd9b38c, 0.035)`，让远处柔和地融进黄昏里。

**核心洞察**：门内那盏黄灯是场景的叙事中心。它照在石桌后面、祖孙三人身上、柿子树的树干上，形成一条贯穿画面的暖色线索。不需要额外的光锥几何体去“强调”它，`PointLight` 本身就会讲故事。

## 五、性能与体验

这个场景在普通笔记本上应该稳定 60fps，关键是：

- **柿子、叶子、萤火虫全部实例化或 Points**，draw call 控制在 30 以内
- **阴影贴图 2048**，只给太阳和门内光
- **程序化材质零贴图请求**，首屏加载只有 JS 体积
- **按需渲染**：如果场景静止，可以降帧或用 `requestAnimationFrame` 节流
- **移动端**：关闭 Bloom，阴影降到 1024，粒子数减半

但比性能更重要的，是**结构层级的清晰度**：

- 屋顶在最高层
- 侧墙在屋顶下方
- 屋体在侧墙下方
- 门、窗、光锥、装饰物都在屋体表面

层级清晰，渲染顺序和阴影计算都自然；层级混乱，多少个 2048 阴影贴图都救不回来。

## 六、如果这个小院要上线

一个 3D 网站，前端是 Three.js，后端其实很薄。按前面聊过的结论：

- **登录、分享、场景配置同步** → 一个 HTTP 云函数，内含多个路由，不需要每个接口一个函数
- **支付订阅**（如果做付费内容）→ 单独一个云函数，配预置并发，处理支付回调的验签和幂等
- **静态资源** → 云存储，图片全部程序化，体积已经很小
- **命名** → 项目叫 `courtyard`，函数叫 `courtyard-api`、`courtyard-payment`，符合“项目-模块-资源”的层级

前端把 Three.js 场景打包成一个模块，后端只提供 JWT 和场景配置，两者解耦，未来想换后端也不影响 3D 部分。

## 七、写在最后

这个黄昏小院，技术上是这样的分工：

- **GLSL** 写了天空、风、萤火虫
- **Three.js** 搭了房子、树、石桌、人、狗、灯光、阴影
- **Canvas** 生成了黑瓦纹理、木纹、石材
- **SVG** 做了页面上的图标和标题
- **云函数** 在背后默默处理登录和同步

但真正让这个场景完成的，不是这些技术，而是**八轮失败之后的一个领悟**：

> **3D 场景的复杂度，从来不来自几何体数量，而来自层级关系。**

屋顶必须盖住一切。这个规则看起来简单，但我在搏风板上反复调了七版参数，都没意识到自己一直在违反它。直到第 8 版，我停止调整搏风板，开始问“它到底该在哪一层”，问题才真正解决。

**几秒钟的顿悟，是七版代码白调换来的。**

Web 3D 今天已经足够成熟。硬件、浏览器、框架、工具链，全都就位。但**真正的难点从来不是 API，而是空间思维**——你能否在脑子里保持一个清晰的三维层级图，在写代码之前就知道谁盖住谁。

剩下的，才是那个黄昏的故事。
